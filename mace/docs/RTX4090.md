# RTX 4090 cluster benchmark

The cluster campaign uses a native Linux environment on `gpunode3`. Docker
reproduction is deferred to a platform with a working Docker installation.
The measured environment and the existing WSL2/3060 Ti environment differ, so
cross-machine ratios include software and host-platform changes.

## Measured results

The completed campaign ran in Slurm job `947238`, using GPU UUID
`GPU-5708370a-8330-67ef-1f36-5af102dc6f18`. All 180,000 replay calls completed:
10,000 calls for each of six implementations on each of three structures.
No new compiled graphs or graph breaks were reported during measurement. NVML
sampling was available throughout and observed no competing compute processes
on the selected GPU. All replay and capacity reports share one environment hash.

| Implementation | 28-atom MPtrj median, ms | 252-atom MPtrj median, ms | Dense 512-atom Si median, ms |
| --- | ---: | ---: | ---: |
| Implicit CUDA | 3.776 | 4.645 | 9.871 |
| Explicit CUDA | 4.164 | 5.047 | 10.105 |
| PyTorch/e3nn | 36.971 | 47.867 | 118.439 |
| cuEquivariance | 37.967 | 44.198 | 51.165 |
| PyTorch/e3nn + compile | 7.098 | 28.823 | 70.985 |
| cuEquivariance + compile | 15.534 | 21.412 | 30.072 |

The implicit implementation is 1.88x, 4.61x, and 3.05x faster than the fastest
tested PyTorch-based entry on these respective cases. Against eager
cuEquivariance, the ratios are 10.05x, 9.52x, and 5.18x. These are within-machine
ratios using the same environment, GPU, inputs, and precision policy.

The 50,176-atom MPtrj case has 2,281,444–2,282,662 directed edges. Implicit CUDA
completed using a sampled process peak of **16.922 GiB** and tracked context peak
of **16.506 GiB**, with a development median of **529.312 ms**. Explicit CUDA also
fit: **16.959 GiB** sampled peak and **522.150 ms** median. All four PyTorch-based
entries reported CUDA OOM at that size. These results demonstrate the 50,000-atom
capacity target on a 24-GiB GPU; large-case timing uses the shorter protocol below.

At 4,096 silicon atoms, eager and compiled cuEquivariance completed at 161.218 ms
and 111.083 ms, versus 44.655 ms for implicit CUDA. Their sampled peaks were
8.098 GiB and 13.635 GiB, versus 1.758 GiB for implicit CUDA. Both e3nn entries
reported OOM at 4,096 atoms; all four PyTorch entries reported OOM at the tested
12,544-, 25,088-, and 50,176-atom MPtrj sizes. These are tested sizes, not a search
for each implementation's exact maximum capacity.

Full samples, p95 latencies, window distributions, warmup samples, allocation
diagnostics, and OOM messages are under `benchmarks/rtx4090/`. See the generated
[tables](../benchmarks/rtx4090/RESULTS.md), [latency plot](../benchmarks/rtx4090/latency.png),
[memory plot](../benchmarks/rtx4090/memory.png), and [audit](../benchmarks/rtx4090/audit.json).

## Protocol

The six entries are implicit CUDA, explicit CUDA, PyTorch/e3nn, cuEquivariance,
PyTorch/e3nn + `torch.compile(default)`, and cuEquivariance +
`torch.compile(default)`. The older `compile` CLI name remains an alias for the
last entry; the new reports use explicit names.

The 28- and 252-atom pinned MPtrj cases and dense 512-atom silicon case use 100
warmup calls and 100 windows of 100 measured calls per entry. All entries replay
the same float32-rounded changing positions and cells through the blocking ASE
interface, with randomized implementation order per window. Wall timing includes
preprocessing, transfers, energy, forces, stress, and completion. CUDA event timing
is supplementary. First-call and warmup samples are retained separately, together
with compilation counters before and after measurement.

Isolated capacity runs use 4,096 silicon atoms, then 12,544, 25,088, and 50,176
MPtrj atoms. They use 10 warmups and 5 windows of 10 calls and are labeled
development timing. Every implementation and size starts in a separate process.
OOM is reported explicitly. These runs measure capacity; they do not satisfy the
full v1 timing protocol. The 50,176-atom supercell is `14 16 8`.

NVML samples process GPU memory every 20 ms, including warmup allocations after
calculator construction. Reports distinguish sampled process peaks, tracked
native capacity, and PyTorch allocator peaks. Shorter transients can be missed.
The observer records other compute processes seen on the benchmark's GPU; each
Slurm job also rejects an assigned GPU that already has a compute process.

## Numerical qualifications

Native conformance tests, explicit-list validation, MH1/LJ invariances, and
force/strain finite differences passed on SM89. Against the official float64
reference, the 252-atom MPtrj case measured energy error `6.48e-8 eV/atom`, force
error `7.92e-6 eV/Å`, and virial error `4.71e-4 eV`; the declared relative virial
tolerance applies.

Stock float32 baseline total energies differ from the native result by
`3.39e-5` to `3.78e-5 eV/atom`, exceeding the strict `1e-5` total-energy target.
The stock model reduces its atomic baseline and interaction energy in float32.
Summing its returned double-precision per-atom energies gives errors below
`7.9e-7 eV/atom`. All four baseline variants have force errors below `8.5e-6 eV/Å`
and pass the declared virial comparison. Validation saves both energy errors;
the timed baseline arithmetic is unchanged. The per-atom diagnostic is not a
claim that the stock float32 total-energy target passes.

Across 100 repeated 252-atom evaluations, the largest native virial component
range is `1.1563e-5 eV` (implicit) and `1.5259e-5 eV` (explicit). This exceeds
the strict `1e-5 eV` repeat target. Energy ranges are `1.99e-8 eV/atom` and force
ranges are at most `1.02e-6 eV/Å`, which meet their targets. The existing strict
checks remain the default; campaign backend diagnostics explicitly report the
repeat gate separately. These are benchmark results with recorded numerical
limitations, not certification of every release gate.

## Reproduction

Synchronize the source, the supplied `mace-ref` checkout, model archives and
manifests, and fixtures to the shared workspace. Exclude local virtual
environments and build directories. If using Git inside the cluster, the origin
is `http://192.168.1.107:3000/luohz/ppf_gpt`; archives and the nested MACE checkout
require separate transfer. Source checksums are the authority for the measured
snapshot.

Run `bash scripts/cluster/setup.sh` on `gpunode9`, then submit from `login2`:

```sh
cd /home15/luohz/ppf_gpt_benchmark
sbatch -p gpu -w gpunode3 --gres=gpu:rtx4090:1 -c 8 --mem=64G \
  -t 00:30:00 -o benchmarks/rtx4090/logs/native-%j.log \
  scripts/cluster/job.sh native

# After the build and native tests complete successfully:
sbatch -p gpu -w gpunode3 --gres=gpu:rtx4090:1 -c 8 --mem=64G \
  -t 02:00:00 -o benchmarks/rtx4090/logs/smoke-%j.log \
  scripts/cluster/job.sh tools/run_cluster_benchmarks.py smoke

# After reviewing validation and the pilot:
sbatch -p gpu -w gpunode3 --gres=gpu:rtx4090:1 -c 8 --mem=64G \
  -t 06:00:00 -o benchmarks/rtx4090/logs/campaign-%j.log \
  scripts/cluster/job.sh tools/run_cluster_benchmarks.py campaign
```

`--start-at NAME` resumes the campaign at a named command after a failure has
been inspected. Commands, return codes, durations, and Slurm job IDs are recorded
in `benchmarks/rtx4090/commands.jsonl`. Retrieve that directory and run
`python scripts/cluster/summarize.py` to render tables, an audit, and plots.
